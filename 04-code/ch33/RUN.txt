What went wrong / caveats:
  - quant_gpt2.py first held Parts F and G too.  GPTQ as first written (one input column at a time, updating the whole
    rest of the table each time) took about 28 s for one 3,072 x 768 map, about 40 minutes for Part F.  The run was
    stopped during Part F (Parts A-E complete and saved), tiny/quant.py's gptq rewritten with lazy batches of 128 columns
    (the 2022 paper's own device; checked identical to the column-at-a-time version on three random cases, max diff 0.0;
    2.0 s for the same map), and Parts F-G moved to quant_gptq.py.  outputs/quant_gpt2.txt was cut after Part E (the
    stopped run had printed only the Part F heading).
  - quant_table.py first carried a leftover no-op line (x = Q.forward_q.__wrapped__ ...); removed after the run; no effect.
  - tiny_quant.py was restarted once before any output to tidy the int8 layer's set-up line; same computation.
  - The 8-bit and 6-bit 'per output channel' and 'per 32' rows score slightly below 32-bit (by up to 0.012); on four
    1,024-token windows of one text that is within the window-to-window spread (Chapter 25); not read as a gain.
  - These scripts ran alongside Chapter 32's timing scripts on other cores; Part H timings carry that load.
  - PyTorch warns that torch.quantize_per_tensor and quantized tensors are deprecated (Part H); reported in 33.9.
